What This Platform Does & Step-by-Step Testing Guide

Guaranteed durable background job execution across distributed worker processes. Zero duplicate runs, zero lost jobs, and automatic crash recovery.

Step 1

📥 Ingestion & Durability

Job is submitted via API. The server commits it immediately to PostgreSQL with version=1. Zero job loss if server dies right after.

Step 2

⚡ Redis Queue Dispatch

Ready jobs are pushed to Redis priority queues (queue:default) for sub-millisecond retrieval. Delayed jobs stay in Postgres.

Step 3

⏱️ Scheduler Daemon (1s)

Every 1s, the scheduler runs SELECT ... FOR UPDATE SKIP LOCKED on Postgres for jobs where scheduled_at <= NOW(), moving them to Redis.

Step 4

🔒 Atomic Lease & Fencing

Worker pops job from Redis and claims an exclusive lease in Postgres: version = version + 1. Prevents split-brain duplicate runs.

Step 5

⚙️ Execution & Heartbeats

Worker executes handler. Sends heartbeats every 2s to renew lease. Checks cancellation flag between iterations to abort cooperatively.

Step 6

🔄 Backoff or Recovery

Success updates SUCCEEDED. Transient errors retry with full-jitter exponential backoff. Dead workers are recovered by the Reaper.

Atomic Leases & FOR UPDATE SKIP LOCKED

PostgreSQL handles concurrency at the row level. Workers skip locked rows simultaneously with zero deadlocks and zero duplicate processing.

🛡️

Version Fencing Tokens

Every lease claim increments jobs.version. If an old worker wakes up after a GC pause, its stale token is rejected by the database.

📈

Full-Jitter Exponential Backoff

Retries randomize wait intervals: $delay = \text{random}(0, \text{base} \times 2^{\text{attempt}})$. Prevents thundering herds from crashing downstream APIs.

🧟

Crash Recovery Reaper

If a worker machine loses power mid-task, its lease expires. The recovery daemon detects expired leases and safely re-enqueues the job.

System Architecture & Exact Distributed Workflow

Deep dive into PostgreSQL durable state, Redis buffers, atomic leasing, and crash recovery

Decoupled Two-Tier Architecture

Traditional message brokers (like RabbitMQ or basic Redis lists) lose state if a worker crashes before acknowledging, or lack transactional ACID guarantees. This platform employs a dual-tier design:

🐘
Tier 1: PostgreSQL (Durable Truth)
  • Authoritative source of truth for all jobs, status, payloads, and attempts.
  • Atomic lease claiming using SELECT ... FOR UPDATE SKIP LOCKED.
  • Optimistic concurrency control with jobs.version fencing tokens.
⚡
Tier 2: Redis (Ephemeral Buffer)
  • Low-latency dispatch buffer: workers block on BRPOPLPUSH.
  • Priority queueing (high priority jobs processed ahead of low priority).
  • Zero disk contention for high-throughput job dispatching.

Autonomous Subsystems

1. API Gateway

FastAPI validates payloads and writes to PostgreSQL with ACID durability before acknowledging receipt to clients.

2. Scheduler Daemon

Runs every 1s. Queries due scheduled and retrying jobs (scheduled_at <= NOW()) and safely promotes them to Redis.

3. Worker Pool (4x)

Autonomous worker processes that claim exclusive leases, execute handlers, emit heartbeats every 2s, and store attempt records.

4. Recovery Reaper

Runs every 5s. Identifies zombie leases where lease_expires_at < NOW() (worker died or hung) and safely reclaims or retries them.

1
Job Ingestion (Client ➔ FastAPI ➔ PostgreSQL)

Client sends POST /api/v1/jobs with payload and priority. Server writes to PostgreSQL with version=1. If immediate, also pushes to Redis (LPUSH queue:default).

2
Delayed Polling (PostgreSQL ➔ Scheduler ➔ Redis)

For jobs with a future scheduled_at, they rest in PostgreSQL. Every 1s, the Scheduler polls SELECT * FROM jobs WHERE status IN ('SCHEDULED', 'RETRY_WAIT') AND scheduled_at <= NOW() FOR UPDATE SKIP LOCKED and pushes them to Redis.

3
Atomic Worker Lease Claiming

Worker pops job ID from Redis, then runs:

UPDATE jobs 
SET status='RUNNING', lease_owner='worker-x', lease_expires_at=NOW()+30s, version=version+1 
WHERE id=:id AND version=:expected_version RETURNING id;

If another worker claimed it first, the version check fails and the second worker safely skips the job.

4
Execution, Heartbeats & Cooperative Cancellation

While the handler runs, a background asyncio task renews the lease in PostgreSQL every 2 seconds. In long-running jobs (like reports), the handler inspects the cancellation token between chunks to stop safely if requested.

5
Completion / Full-Jitter Exponential Backoff

On success, job updates to SUCCEEDED. On transient failure, worker calculates full-jitter backoff: delay = random(0, base * 2^attempt), schedules a retry, and updates status to RETRY_WAIT.

Split-Brain Prevention via Version Fencing

Suppose Worker A claims a job, but experiences an extreme OS freeze or network pause. The lease expires, and the Recovery Reaper reassigns the job to Worker B (incrementing version to 3). When Worker A finally wakes up, its attempt to write with version=2 is rejected because the database requires WHERE version=2, but the row is now version=3! No duplicate or corrupted writes can ever occur.

Row-Level Locking without Lock Contention

By using PostgreSQL's FOR UPDATE SKIP LOCKED, worker processes and the scheduler daemon never wait for locks held by other transactions. They instantly skip locked rows and grab the next available job, maintaining high throughput under concurrent load.
